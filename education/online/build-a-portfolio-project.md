## Goal

You build and publish a focused project that demonstrates a skill clearly enough for an instructor, recruiter, or client to evaluate.

## Preconditions

- A target skill or role, such as data analysis, web development, design, writing, or cybersecurity.
- Enough baseline knowledge to finish a small project.
- A place to store and present the work, such as GitHub, a portfolio site, Behance, or a PDF.

## Steps

1. **Choose a narrow audience and outcome.** Decide who should care about the project and what ability it proves. → *Expect:* a one-sentence project purpose.
2. **Define the minimum finished version.** List the core features, deliverables, data, or artifacts required for a complete first version. → *Expect:* the project can be finished without endless expansion.
3. **Use realistic constraints.** Pick a public dataset, mock brief, accessible materials, or problem you are allowed to share. → *Expect:* no private or proprietary content is needed.
4. **Plan the work in milestones.** Break the project into setup, build, review, polish, and publish tasks. → *Expect:* each milestone has a visible deliverable.
5. **Build the core artifact first.** Implement the smallest version that proves the main skill before adding extras. → *Expect:* a working draft exists early.
6. **Document decisions as you go.** Keep notes on assumptions, tradeoffs, sources, and mistakes fixed. → *Expect:* your final write-up has real substance.
7. **Test or review the result.** Check the project against requirements, have someone try it, or compare it to professional examples. → *Expect:* defects and confusing parts are identified.
8. **Publish with context.** Include the final artifact, screenshots or samples, setup instructions if relevant, and a short case-study explanation. → *Expect:* a reviewer can understand the project without interviewing you.
9. **Add a reflection.** State what you would improve next and what you learned. → *Expect:* the project shows judgment, not just output.

## Decision points

- Project scope exceeds available time → cut features until the core proof remains.
- Work uses sensitive data → replace it with public, synthetic, or anonymized data.
- Target role has standard artifacts → match the expected format, such as a repo README, case study, notebook, or writing sample.

## Failure modes & recovery

- **F1 Scope creep:** detect unfinished extras delaying publication → freeze new features and ship the minimum version.
- **F2 Weak presentation:** detect a finished artifact with no explanation → add problem, approach, tools, result, and lessons learned.
- **F3 Unclear ownership:** detect copied templates or tutorials without attribution → cite sources and explain what you changed or built yourself.
- **F4 Broken demo:** detect install errors, dead links, or missing files → test from a clean device or account and fix the public version.

## Verification

The project is published in a shareable location, includes enough context to evaluate it, and demonstrates the target skill through a finished artifact.

## Variations

- Software: include a README with setup, usage, screenshots, and known limitations.
- Data analysis: include data source, cleaning steps, analysis notebook, and conclusions.
- Design: include the brief, process, final screens, and rationale for major choices.

## Safety & privacy

Low risk. Do not publish private employer, school, client, or user data. Attribute open-source code, images, datasets, and templates according to their licenses.
